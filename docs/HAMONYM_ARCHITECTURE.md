# HAMONYM_ARCHITECTURE.md — System Architecture & Design Guide

**סטטוס:** v1 (פרקים 0–11 — יציבים. AI Framework המלא, Data Flows ו-Integrations המפורטים יתווספו כשיתייצבו)
**תאריך:** 2026-07-14

## 0. מטרת המסמך ומצב הארכיטקטורה

מסמך זה אינו מתעד קוד. מטרתו להסביר איך מערכת **המונים** בנויה **היום**, מדוע היא בנויה כך, ולאילו דפוסים היא מתכנסת.

זהו לא מסמך "כך בנויה המערכת" (שמרמז על תכנון סופי), וגם לא מסמך "Target Architecture" (שמתאר מערכת שעדיין לא קיימת). זהו מסמך שמתאר **אבולוציה**: המונים לא נבנתה לפי ארכיטקטורה אחת מראש — היא התפתחה, ודפוסים טובים (`CurrentEntityService`, `AnalyticsRangeService`, ה-Advisor Framework) מתגבשים מתוך ניסיון, לא מתכנון תאורטי מראש.

> "המונים" היא מערכת שנמצאת בהתפתחות פעילה. חלק מהאזורים כבר עברו סטנדרטיזציה (כגון Framework ה-Advisors ומערכת ה-Context), בעוד שאזורים אחרים עדיין משקפים החלטות היסטוריות. מטרת המסמך אינה להסתיר את הפערים, אלא להפוך אותם לגלויים ומודעים, כך שכל פיתוח חדש יתכנס לאותם עקרונות במקום להרחיב את חוסר האחידות.

כל פרק שמתאר שכבה בקוד (Frontend, Backend) בנוי בשלושה חלקים: **היום** (מה קיים בפועל, מבוסס על קריאת קוד אמיתי), **למה** (ההקשר ההיסטורי), **הכיוון** (לאן מתכנסים, לא כיעד מחייב).

מפתח חדש שקורא את המסמך הזה ואז פותח קובץ קוד אמור לזהות את מה שתואר — לא להתבלבל.

> **בכל פיתוח חדש, ברירת המחדל היא להתאים את הפתרון לארכיטקטורה הקיימת. רק כאשר הארכיטקטורה עצמה אינה מספקת מענה, מרחיבים אותה בצורה מתועדת.** זו הסיבה שנכתבים כל כך הרבה מסמכי Vision ו-Spec בפרויקט הזה — לא כדי להאט את הפיתוח, אלא כדי שהמערכת תתפתח בעקביות, בלי שכל פיצ'ר ימציא לעצמו דפוסים חדשים.

## 1. סקירה כללית

המונים היא פלטפורמת SaaS לניהול גיוס המונים עבור עמותות. המערכת מלווה את מחזור החיים המלא:

```
הרשמת עמותה
    ↓
בדיקת ואישור עמותה  (Approval Agent)
    ↓
יצירת קמפיינים
    ↓
פרסום
    ↓
קבלת תרומות
    ↓
סליקה (Cardcom)
    ↓
קבלות
    ↓
ניהול תורמים
    ↓
אנליטיקה  (Analytics Vision)
    ↓
AI Advisors
```

## 2. עקרונות שכבר נכונים היום

אלה לא שאיפות — נבדקו ואומתו בקוד בפועל השבוע:

- **מקור אמת יחיד לכל state חוצה-מסכים.** עמותה פעילה, תפקיד פעיל וטווח זמן לניתוח מנוהלים כל אחד ב-signal service יחיד (`CurrentContextService`, `CurrentEntityService`, `AnalyticsRangeService`) — לא מחושבים מקומית בכל קומפוננטה.
- **ה-AI אינו מקור אמת.** בכל Advisor קיים (`CampaignAdvisorAgent`), העובדות מחושבות בקוד לפני קריאת ה-LLM; ה-LLM מנסח ומתעדף, לא ממציא.
- **Controllers דקים בבקאנד.** בכל מודול שנבדק (`reports`, `dashboard`, `campaigns`, `entities`), ה-Controller מתרגם בקשת HTTP לקריאת שירות ומחזיר JSON — לא מקבל החלטות עסקיות.

## 3. עקרונות שאנחנו מתכנסים אליהם (לא נכונים באופן אחיד עדיין)

- הפרדה בין לוגיקה עסקית לגישה לנתונים (Business Service מול Tools/Repository) — קיימת רק במסגרת ה-Advisors, לא בבקאנד הכללי (ר' §10).
- קומפוננטות Frontend דקות עם לוגיקה בשירותים ייעודיים — קיים חלקית ובאופן לא אחיד (ר' §9).
- ADR לכל החלטה משמעותית — התחיל עם `DECISIONS.md`, עדיין לא מכסה החלטות היסטוריות.

## 4. Evolution Rules — איך מוסיפים דבר חדש

זו לא תיאוריה — זו איך שהפרויקט כבר עובד בפועל, רק שעד עכשיו זה לא היה כתוב:

1. **קודם מחפשים דפוס קיים.** לפני שכותבים קוד, בודקים אם משהו דומה כבר נבנה (למשל: לפני `AnalyticsRangeService` נבדק איך `CurrentContextService` פותר בעיה דומה).
2. **אם אין דפוס — יוצרים אחד, ומתעדים למה.** יצירת דפוס חדש היא החלטה, לא צירוף מקרים — היא נכנסת ל-`DECISIONS.md`.
3. **לא משכתבים קוד ישן רק כדי להתאים אותו לדפוס החדש.** קוד ישן שעובד נשאר כמו שהוא עד שיש סיבה אמיתית לגעת בו.
4. **רפקטורינג נעשה רק כשיש לו ערך עסקי מוחשי** — לא "כי זה יותר נקי". לדוגמה: כפילות שכבר גרמה לבאג אמיתי (ר' `DECISIONS.md` — מטמון הדשבורד).

## 5. איך מתקבלות החלטות בפרויקט

התהליך שכבר קורה בפועל בכל Feature משמעותי:

```
Vision              (למה בכלל? — מסמך קצר, לא טכני)
    ↓
Spec                (מה בדיוק נבנה, ואיך זה מתחבר למה שקיים)
    ↓
Discussion           (סקירה, ביקורת, חידוד — לפני כתיבת קוד)
    ↓
Implementation       (בקומיטים קטנים, כל אחד נבדק בנפרד)
    ↓
Completion Report    (מה נבנה, מה אומת, מה נשאר בכוונה בחוץ)
    ↓
DECISIONS.md         (למה, לא רק מה)
```

הסדר הזה הוא לא בירוקרטיה — הוא מה שקרה בפועל עם `ANALYTICS_VISION.md` → `GLOBAL_DATE_RANGE_SPEC.md` → סבבי סקירה → 4 קומיטים נפרדים → דיווח → `DECISIONS.md`. Feature חדש אמור לעבור את אותו מסלול.

## 6. Architectural Maturity

איפה מותר לצפות ליציבות, ואיפה עדיין סביר שדברים ישתנו:

| תחום | מצב |
|---|---|
| Context (עמותה/תפקיד/טווח פעילים) | 🟢 יציב |
| Advisor Framework | 🟢 יציב |
| Analytics (שכבות Overview/Analysis/Advisor/Investigation) | 🟡 בהתהוות |
| Backend Layering (Repository/Tools כללי) | 🟡 מתפתח |
| Frontend Pattern (Feature Services) | 🟡 מתפתח |

## 7. ארכיטקטורת המערכת ברמה הגבוהה

```
Angular Frontend
      ↓
REST API (Express)
      ↓
Business Services  (מכילים גם SQL וגם לוגיקה — ר' §10)
      ↓
PostgreSQL (Supabase)
      ↓
External Services: Cardcom · OpenAI · GuideStar · Google OAuth
```

זו רמת התיאור היחידה שנכונה במדויק לכל מודול בבקאנד — הפירוט בפרק 10 מסביר למה השכבה "Business Services" לא מתפצלת הלאה כמו שהיה אפשר לצפות.

## 8. Domain Model

מושגי הליבה של המערכת — **תיאור דומיין, לא בהכרח מבנה טבלאות במסד הנתונים.** אם אתה מחפש טבלה בשם `donors` ולא מוצא — זה בכוונה (ר' למטה).

- **User** — משתמש במערכת, יכול להחזיק כמה תפקידים (מנהל עמותה, שגריר, קמפיינר, תורם).
- **Entity** — עמותה. הישות המרכזית שאליה כל שאר הנתונים משויכים.
- **Campaign** — קמפיין גיוס של עמותה.
- **Donation** — תרומה בודדת, עם סטטוס (`pending`/`paid`/`failed`).
- **Donor** — תורם. נגזר מהתרומות (לפי אימייל/טלפון), לא בהכרח טבלה עצמאית בכל מקום.
- **Ambassador** — שגריר שמגייס עבור קמפיין ספציפי.
- **Receipt** — קבלה שמופקת עבור תרומה.
- **Audit Log** — תיעוד פעולות רגישות במערכת.

## 9. Frontend Architecture

### היום

```
Component
    ↓
HttpClient (ישירות, ברוב המסכים)
    ↓
REST API
```

במסכים חדשים יותר (Dashboard, Reports, Campaigns) מתחילים להופיע Context Services ו-signals (`CurrentEntityService`, `AnalyticsRangeService`) כמקור אמת חוצה-קומפוננטות — אבל רוב הקריאות ל-API עדיין נעשות ישירות מתוך הקומפוננטה עם `HttpClient`, בלי שכבת Service ייעודית ביניים.

### למה

רוב המסכים נבנו לפני שהתגבשה תבנית ה-Context Services וה-signals. כשמסך בודד היה עצמאי, קריאת HTTP ישירה מתוכו הייתה הפתרון הפשוט ביותר.

### הכיוון

```
Page
    ↓
Context Service   (עמותה פעילה, טווח זמן — כבר קיים)
    ↓
Feature Service    (קריאות API, לא בקומפוננטה עצמה)
    ↓
REST API
```

לא כיעד מחייב לרפקטור מסכים קיימים — אלא כדפוס שמסך חדש אמור לאמץ מהיום הראשון.

## 10. Backend Architecture

### היום

```
Route
    ↓
Controller   (מתרגם HTTP בלבד)
    ↓
Service      (לוגיקה עסקית + SQL גולמי + לעיתים קריאות למערכות חיצוניות — יחד)
    ↓
PostgreSQL
```

נבדק בפועל מול `reports.service.js`, `dashboard.service.js`, `campaigns.service.js`, `entities.service.js` — בכולם ה-Service מכיל גם את הלוגיקה העסקית וגם את שאילתות ה-SQL הגולמיות, ללא שכבת Repository או Tools נפרדת. שכבת `Tools` הנפרדת קיימת **רק** במסגרת ה-Advisors (`agents/approval/tools/`, `agents/campaign-advisor/tools/`) — זה דפוס ספציפי ל-AI, לא דפוס בקאנד כללי.

### למה

בתחילת הפרויקט הועדפה פשטות על פני שכבות נוספות. כל Service היה קטן יחסית, ולכן פיצול ל-Repository היה מוסיף מורכבות בלי ערך ממשי. כיום, כאשר חלק מה-Services גדלים (ר' `reports.service.js` — כמעט 300 שורות אחרי Phase 1), מתחילים להופיע דפוסים חדשים במקומות שבהם יש לכך הצדקה — כמו שכבר קרה במסגרת ה-Advisors.

### הכיוון

```
Route
    ↓
Controller
    ↓
Business Service   (לוגיקה עסקית בלבד)
    ↓
Shared Tools / Data Access
    ↓
PostgreSQL
```

כיוון שאליו אפשר להתקדם כשיהיה ערך אמיתי בכך (למשל: שאילתה שחוזרת על עצמה במספר Services) — לא רפקטור גורף.

## 11. מסמכי הארכיטקטורה

מסמך זה הוא מסמך העל. מתחתיו מסמכים ייעודיים, כל אחד מתאר תחום אחד — וזו כבר לא רק תצפית, אלא **המדיניות** לכל Feature חדש (ר' §5):

```
HAMONYM_ARCHITECTURE.md   (המסמך הזה — למה המערכת בנויה כך)
    ↓
Vision                    (למה בכלל בונים את זה)
    ↓
Functional Spec           (איך זה מתחבר לארכיטקטורה הקיימת)
    ↓
Implementation
    ↓
DECISIONS.md              (מה הוחלט ולמה)
```

המסמכים הקיימים היום:

```
├── ANALYTICS_VISION.md                       — פילוסופיית האנליטיקה, 4 השכבות
├── GLOBAL_DATE_RANGE_SPEC.md                  — Phase 1 של ה-Analytics Vision
├── CAMPAIGN_ADVISOR_AGENT_MVP_SPEC.md         — אפיון עסקי ל-Advisor הראשון
├── CAMPAIGN_ADVISOR_AGENT_FUNCTIONAL_SPEC.md  — ארכיטקטורת ה-Advisor Framework
├── APPROVAL_AGENT_CONTEXT.md                  — ה-Advisor השני, יומן מימוש
├── SUPER_ADMIN_CONTEXT.md                     — מודול ה-Super Admin
└── DECISIONS.md                               — ADR: מה הוחלט ולמה
```

מסמכים ייעודיים נוספים (למשל על מודול הדוא"ל או הרשאות) ייווצרו כשהתחום שלהם יתייצב מספיק כדי להצדיק מסמך — לא לפני.
