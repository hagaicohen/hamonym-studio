# Legal identity uniqueness — local implementation, not deployed

## Supported mapping

The existing Israeli entity types map to a fixed `registration_jurisdiction`
of `IL`. This is an application namespace, not an international entity model.

| Existing entity type | identifier_type |
| --- | --- |
| association | association_number |
| chalatz | company_number |
| political_party_new / political_party_registered | party_number |
| sole_exempt / sole_registered | business_number |

The paired lifecycle/tax classifications share a number namespace. Identity
scope is generated by PostgreSQL from the existing type; clients cannot choose
an arbitrary namespace to evade uniqueness. No extra number requirement or
length/checksum rule is introduced. The currently hidden party-number field
and its existing onboarding completeness rules are not redesigned here.

Normalization removes whitespace and common hyphen/dash separators, preserves
leading zeroes and does not convert numbers to integer or remove other
characters. Original `registration_number` values are never rewritten.

The migration rejects unknown types and conflicting normalized identities
among non-deleted rows before changing columns/indexes. It then adds three
generated fields and a unique index on jurisdiction, type and normalized
number. Only after the replacement index succeeds is the old global raw-number
index removed. Original records, statuses, ownership, documents and audit
history remain intact. No automatic merging or cleanup exists.

The read-only pilot inventory found one draft, one pending application and
four soft-deleted rows, all associations, with no live normalized collision.
The `580123456` collision is between a live draft and a deleted row and is
allowed. A fresh inventory is mandatory at future deployment time.

All non-deleted statuses participate, including rejected and suspended.
Soft-deleted identities are excluded. No organization restore endpoint exists
currently; the same unique index blocks a conflicting `deleted_at = NULL`
update, including direct SQL. No restore flow or permission was added.

## Rollback

Pause writers and roll back identity-aware application code in coordination
with the schema. Run the rollback script in one transaction. It first checks
whether the old global raw-number index can be reinstated. New records valid
in separate namespaces, or repeated blank raw numbers, can make this impossible.
In that case rollback stops and leaves the new schema/data intact; obtain a
decision rather than deleting/merging records. The tested compatible rollback
recreates the old index first, then removes only the new index, generated
fields and pure helper functions. No automatic backup restoration is allowed.

## API and UI

`POST /api/entities/registration-availability` uses the existing authenticated
entity route tree. It returns `available` and, only for an existing member or
an authorized platform administrator, `existingEntityId` and the appropriate
management scope. Admin permissions reuse the existing authenticated request
claims; body-supplied authorization flags are ignored. Excluding an edited entity requires membership. Strangers
get no names, IDs, statuses or internal information and receive no membership.
There is only an existing manager-invitation flow, not a public join-request
flow, so the UI offers support instead of an unimplemented join action.

Create and update recheck the identity server-side. The database index remains
the final authority under concurrency, including direct writes and all roles.
Only identity-specific unique constraints map to HTTP 409 with
`DUPLICATE_LEGAL_IDENTIFIER`; review-transition 409s remain separate.

The shared inline checker is used in registration and number editing, with a
400ms debounce, cancellation of stale requests, a small spinner, neutral
available feedback, duplicate feedback and an authorized management link.
Failures/malformed responses never claim availability. Confirmed duplicates
disable continuation/draft creation/save; correcting the number clears the
block. Backend checks remain mandatory even when lookup is unavailable.

## Verification and separate deletion finding

`scripts/test-organization-identity-postgres.cjs` and the existing lifecycle
runner create/drop disposable databases on the local Docker container only.
They exercise migration collision/unknown-type preflight, normalized aliases,
same names, scopes, all statuses, updates, permissions, concurrent creation,
direct writes, restoration conflicts and rollback failure/success. Angular
tests mock HTTP and cover debounce, stale cancellation, errors, reload and
duplicate recovery. No shared writes or financial provider calls are involved.

Separate read-only deletion review: soft deletion marks the organization and
campaigns deleted without checking for financial activity. Financial history
is not erased by that soft-delete function. Permanent Admin deletion explicitly
attempts receipt deletion and entity deletion; its ultimate effects also depend
on database financial/FK protections. No closure/deletion behavior, permission,
trigger or financial rule was changed in this work. That review needs its own
scope before any policy change.
